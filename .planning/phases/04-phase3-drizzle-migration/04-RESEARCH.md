## Summary

Phase 4 is a pure infrastructure task: generate and commit the missing Drizzle migration for the three schema changes introduced in Phase 3 (versions/drafts on Posts, featuredImage upload field on Posts, navItems array on SiteSettings). Development works because `push: true` auto-applies schema changes, but production (`push: false`) would crash on missing columns and tables.

The migration workflow is already established and well-tested from Phase 1 and Phase 2. Two migration files already exist in `src/migrations/`: `20260311_143013.ts` (Phase 1 foundation) and `20260312_001714.ts` (Phase 2 content collections). The `migrate:create` command compares the most recent JSON snapshot (`20260312_001714.json`) against the current Payload config and generates a diff containing only the delta -- no manual SQL authoring required.

**Primary recommendation:** Run `npx payload migrate:create`, verify the generated SQL covers all three schema changes, update `src/migrations/index.ts` if not auto-updated, optionally add a data migration to set `_status: 'published'` on existing posts, and commit. Then verify with `npx payload migrate` against a clean or dev database.

## Architecture Patterns

### Migration File Structure (Established)

```
src/migrations/
  20260311_143013.ts       # Phase 1: foundation (users, tenants, posts base)
  20260311_143013.json     # Phase 1: Drizzle schema snapshot
  20260312_001714.ts       # Phase 2: content collections (pages, media, site-settings, posts columns)
  20260312_001714.json     # Phase 2: Drizzle schema snapshot
  YYYYMMDD_HHMMSS.ts       # Phase 3: <-- THIS IS WHAT WE GENERATE
  YYYYMMDD_HHMMSS.json     # Phase 3: <-- schema snapshot auto-generated
  index.ts                 # Migration registry -- imports and exports all migrations
```

### How `migrate:create` Works

1. Payload reads the most recent `.json` snapshot file from `src/migrations/` (currently `20260312_001714.json`)
2. Payload builds the target Drizzle schema from the current `payload.config.ts` (including all collection definitions)
3. Drizzle Kit diffs the two schemas and generates SQL statements for the delta
4. Output: a new `.ts` file (with `up()` and `down()` functions containing SQL) and a new `.json` snapshot
5. Since Payload 3.40.0, `migrate:create` does NOT require a database connection (`disableDBConnect: true` is set internally)

**Confidence:** HIGH -- verified via GitHub issue #12582 (resolved in PR #12596, Payload 3.40.0). We are on 3.79.0.

### Expected Schema Changes (Phase 3 Delta)

Based on analysis of current collection configs vs Phase 2 migration snapshot:

#### 1. Posts: `versions: { drafts: true }`

This adds:
- **`_status` column** on `posts` table -- an ENUM type (`enum_posts_status`) with values `draft` and `published`
- **`_posts_v` table** -- version history table mirroring all `posts` columns plus version metadata:
  - `id` (serial primary key)
  - `parent_id` (FK to `posts.id`)
  - `version_*` columns (mirrors of each `posts` field, prefixed)
  - `latest` (boolean) -- marks the most recent version
  - `created_at`, `updated_at` timestamps
  - `autosave` (boolean) -- if autosave is enabled
- **`_posts_v` foreign keys and indexes**
- **ENUM type** `enum__posts_v_version_status` for the version table's status column
- **ENUM type** `enum_posts_status` for the main table's `_status` column

#### 2. Posts: `featuredImage` upload field

This adds:
- **`featured_image_id` column** on `posts` table (integer, FK to `media.id`, ON DELETE set null)
- **`featured_image_id` index** on `posts` table
- On the `_posts_v` table: **`version_featured_image_id`** column mirroring the relationship

#### 3. SiteSettings: `navItems` array field

This adds:
- **`site_settings_nav_items` table** with columns:
  - `_order` (integer, NOT NULL)
  - `_parent_id` (integer, FK to `site_settings.id`, ON DELETE cascade)
  - `id` (varchar, primary key)
  - `label` (varchar, NOT NULL)
  - `url` (varchar, NOT NULL)
- **Indexes** on `_order` and `_parent_id`

**Confidence:** HIGH for columns 2 and 3 (standard Payload field-to-column mapping established in Phase 1/2 migrations). MEDIUM for exact version table column naming conventions (version table naming is `_posts_v`, column prefixes like `version_*` are Payload conventions observed in community but not verified against 3.79.0 source -- the generated migration will be authoritative).

### Data Migration Consideration

When `versions: { drafts: true }` is added to an existing collection:

- **Existing posts will have `_status = NULL`** until resaved
- Posts with `NULL` _status may not appear in admin UI or API queries that filter by `_status: 'published'`
- **Recommended:** Include a data migration step that sets `_status = 'published'` on all existing posts

However, for THIS project:
- **Production database has no data yet** -- this is a greenfield project, not yet deployed
- **Development database uses `push: true`** and has already had the schema pushed
- Data migration is optional but **recommended as defensive practice** -- if any seeded/test data exists in production staging, it would be affected

**Recommendation (Claude's Discretion):** Include a simple `UPDATE posts SET _status = 'published' WHERE _status IS NULL` in the migration's `up()` function, after the schema DDL. This is a no-op on empty tables and protects against any pre-existing data.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Migration SQL | Write ALTER TABLE statements manually | `npx payload migrate:create` | Payload/Drizzle generates complete, correct DDL from config diff; includes indexes, FKs, enums, version tables |
| Schema snapshot | Manually create JSON snapshot | Auto-generated by `migrate:create` | JSON snapshot format is internal to Drizzle Kit; manual creation is error-prone and fragile |
| Migration registry | Manually update `index.ts` | Check if `migrate:create` auto-updates it; if not, add import manually | Must follow established pattern from Phase 1/2 entries |

**Key insight:** The entire migration is auto-generated. The only manual work is: (1) running the command, (2) verifying the output, (3) optionally adding a data migration line, and (4) committing.

## Common Pitfalls

### Pitfall 1: Push/Migrate Conflict on Dev Database

**What goes wrong:** Running `npx payload migrate` on a dev database that was built via `push: true` causes errors because the `payload_migrations` table records show only Phase 1 and Phase 2 migrations were applied, but the database schema is already up-to-date (pushed by Drizzle).
**Why it happens:** Push and migrate are two independent schema-sync mechanisms. Payload warns: "do not mix push and migrations with your local development database."
**How to avoid:** Do NOT run `npx payload migrate` against the dev database that has been using `push: true`. Instead:
  - Generate the migration: `npx payload migrate:create` (no DB connection needed since 3.40.0)
  - Verify the generated SQL by reading the `.ts` file
  - To actually test the migration, use a fresh database (e.g., drop and recreate the Docker Compose volume, or use a separate DATABASE_URL)
**Warning signs:** Error messages about tables/columns already existing, or "relation already exists" errors.

### Pitfall 2: Missing `index.ts` Update

**What goes wrong:** The new migration file is generated but not registered in `src/migrations/index.ts`, so `payload migrate` does not see it.
**Why it happens:** Payload's `migrate:create` may or may not auto-update `index.ts` depending on version. In Phase 1 and Phase 2, the registry was auto-generated.
**How to avoid:** After running `migrate:create`, verify that `src/migrations/index.ts` includes the new migration import and export entry. If not, add it manually following the established pattern.
**Warning signs:** `payload migrate` reports "Nothing to migrate" even though the new file exists.

### Pitfall 3: Existing Posts Missing `_status`

**What goes wrong:** After enabling `versions: { drafts: true }`, existing posts have `_status = NULL` and don't appear in draft-aware queries.
**Why it happens:** Payload doesn't backfill `_status` on existing rows; it only sets it on new creates/updates.
**How to avoid:** Add `UPDATE posts SET _status = 'published' WHERE _status IS NULL` to the migration's up() function.
**Warning signs:** Posts disappear from admin UI after migration; API queries return empty results.

### Pitfall 4: Version Table Not Populated for Existing Documents

**What goes wrong:** Existing posts have no entries in `_posts_v`, so the version history is empty.
**Why it happens:** Version rows are only created when a document is saved through Payload's API.
**How to avoid:** For a production system with existing data, you'd need a data migration that creates version entries. For THIS project (greenfield, no production data), this is not a concern.
**Warning signs:** Version history tab is empty for pre-migration documents.

### Pitfall 5: ENUM Type Naming Conflicts

**What goes wrong:** `CREATE TYPE` fails because the enum type already exists.
**Why it happens:** If running migration against a DB that was already pushed with the new schema.
**How to avoid:** Only run `payload migrate` against databases that haven't been pushed. Use `IF NOT EXISTS` in manual SQL if needed.
**Warning signs:** `ERROR: type "enum_posts_status" already exists`

## Open Questions

1. **Whether `migrate:create` auto-updates `index.ts`**
   - What we know: In Phase 1 and Phase 2, `index.ts` was present and correct after running `migrate:create`. The file appears to be auto-generated.
   - What's unclear: Whether this is guaranteed behavior or whether it was manually created.
   - Recommendation: Run `migrate:create` and check. If `index.ts` is not updated, manually add the new entry following the established pattern. LOW risk.

2. **Exact version table column naming**
   - What we know: Payload creates a `_posts_v` table with `version_` prefixed columns. The `latest` boolean column is critical.
   - What's unclear: Exact column names for all fields (e.g., `version_title`, `version_content`, `version_featured_image_id`).
   - Recommendation: Let `migrate:create` generate it -- the generated SQL will be authoritative. Just verify it includes the expected tables/columns.

3. **Whether regenerating types (`payload-types.ts`) should be part of this phase**
   - What we know: Phase 3 already has stale type casts (noted in tech debt audit). Regenerating types would fix those.
   - What's unclear: Whether this is in scope for Phase 4 (pure migration phase) or Phase 5 (tech debt).
   - Recommendation: Include a `npm run build` step which regenerates types as a side effect. This ensures types match the migration schema. Not the primary goal but a useful byproduct.
